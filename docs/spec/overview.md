# 全体仕様・SDKの責任境界

統合仕様1.0／2026-09-17。必須事項の実装契約。性能の実証とは別。

## 1. 目的

RouteLoomは、端末の増設・移動・撤去、経路断、再起動、電池端末の起床を通常動作として扱うMesh通信SDKである。利用者は宛先と配送条件を指定し、普段の経路を手書きしない。ハードウェアだけでなく組み込みAPIとPC接続APIを提供対象にする。

無線の第一実装はESP-NOW／Wi-Fi LR。LoRaや別Transportを将来追加しても機器Identity・メッセージの意味・アプリAPIを再設計しない境界を持つ。一方、異なる無線の時間・容量制約を同じと偽らない。

## 2. 配置と識別

1ノードは同時に1論理ネットワークへ所属する。1ネットワークに最大4Gatewayを初期対象とし、30〜50ノードを通常規模、100ノードと10無線hopを試験対象にする。論理機器台帳の実装予算128は性能認定100とは別。

GatewayはPC等への出口であり、管理者であることを意味しない。2Gatewayは異なる宛先でもよい。別ネットワークは鍵・経路・設定を分離し、PCが両方を管理しても暗黙に転送しない。

宛先は特定Node/Gateway、許可された任意Gateway、serviceを扱う。任意宛先は送信元が各配送ラウンドで具体的な受信先を選ぶ。途中のRelayは別のPCを勝手な成功先にしない。

## 3. 分担

| アプリ／運用が指定 | SDKが実施 |
|---|---|
| payload、宛先、期限、優先度 | 経路、送信、再送、重複、結果 |
| 中継許可、活動予算、起床条件 | 可用性確認、中継参加・離脱、保存と復帰 |
| 参加承認の方針・承認主体 | 発見、認証、承認要求、所属の発行・削除 |
| 設定の意味、アプリ適用結果 | 権限確認、版管理、配送、監査 |
| 機器名称や位置、センサー判定 | opaque payloadの安全な伝送 |

標準ポリシーは提供するが用途を焼き込まない。例：事前許可したIdentityの自動Join、初回の人間承認、期間付き参加許可。センサーの種類から勝手に優先度やrelay権限を決めない。

## 4. 必須の性質

- Identity、所属、無線経路、暗号session、PC接続sessionを分離する。
- 起床・経路変更だけで初回Joinに戻さない。
- 認証済み受理と最終配送とアプリ適用を分け、結果不明を表現する。
- 全キュー・探索・転送・再組立・ログに上限と期限を置く。
- 管理合意が不在でも有効な設定の通常通信と局所修復は可能な限り続ける。
- 自動化は合法なRF構成と能力範囲から逸脱しない。
- 無線がない場所、全端末が眠る構成、過半数不在、全帯域妨害をソフトだけで解決したと表示しない。

## 5. 初期範囲と拡張

初期必須：全LR、適応250/500、固定250、参加、複数出口、撤去・交換、下り配送、認証暗号化、Remote Config、Deep Sleep復帰、USB/PC窓口、CLI/TUI、干渉観測、協調チャンネル移行。

拡張契約は今定義するが初期RFには含めない：SX1262 LoRa、5GHz、通常AP接続併用、BLE共存、定常的な複数Radio Domain、自動異ネットワークbridge、同期受信窓を使った眠る中継。

OTAは通常通信と分離した管理機能として設計する。実装認定まではUNSUPPORTEDを返す。未実装機能をcapabilityに載せない。

## 6. 使用例

中継兼アプリ端末を撤去する前に小型Relayを追加すると、新Relayは既存網を通じて参加する。上流・下流の到達を確認後に経路を引き継ぐ。先に撤去された場合も有効な予備または探索で復旧する。機器の所属や宛先は変えない。

アプリの基準構成をルーティングに焼き込まない。同じ場所の別ノードを経由する経路も認める。
