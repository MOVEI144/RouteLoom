## Procedure as run

1. Inventory → full erase (`erase/`) → full flash of the DevRam field
   images. **The field images then boot-looped**: an erased board has no
   BoardConfig (`rlcfg`) and v2 field images refuse RF without it. After
   eight restarts (~95 s) the fail policy put all three boards into a
   30-minute deep sleep with USB gone. They were recovered by
   `tools/hil/catch_wake.py --rom-direct` at the first timer wake, which
   wrote the maintenance (setup) image (`recover/`). See finding F2.
2. v2 provisioning, per board: full flash of the setup image
   (`CONFIG_ROUTELOOM_MAINTENANCE_CONSOLE=y`, same chip/role/security as the
   field image) → `benchcfg`/`benchsecret` commit of the RLC1 BoardConfig
   (NodeId, STA MAC, chip, role, security, channel 6, network
   `af8eeadf`; DevRam PSK and, for the bridge, the site USB secret) →
   NVS read-back → app-only write of the field image (ota_0 + blank
   otadata, no boot in between) → NVS read-back → reset and boot capture.
   The Mesh Lab headless provisioner could not be used (finding F10); the
   run used its building blocks (`rlc1_document`, `board_config_commit`,
   `Provisioner`, `CtlOffice`) from a bench script.
3. The host daemon ran with `--site-authority` of a fresh development lab
   site (`lab-site-init`, SiteId `e6211d27e16bd181`) and
   `--admission-profile bench-v1` for both phases, so the 2-per-minute
   contract limit did not pace the 100-message campaigns.
4. Traffic: `accepted_traffic.py` (legacy `send`, 5 s pace, RELIABLE,
   5 s deadline) with the receiver console captured and matched by
   `correlate_receipts.py`; upstream traffic from bench images with
   `CONFIG_ROUTELOOM_HIL_SEND_DESTINATION=0x1`, `…_COUNT=100` (one send
   every 2 s from 10 s after boot) collected from API1 `messages.read`.
5. Forced 2 hop: bridge and endpoint images with
   `CONFIG_ROUTELOOM_HIL_DROP_RX_MAC` naming each other, so Node1 and Node3
   can only meet through Node2.
6. Reset type: every reset in this round is an EN reset through the USB
   Serial/JTAG RTS line or the esptool ROM reset (`software`/chip reset in
   the matrix vocabulary). No power removal was performed.

## P01 — partitions, boot, NVS retention

- Every boot log shows `boot: Loaded app from partition at offset 0x40000`
  and `rl_flash: image: sdk=0.1.0 layout=PT-4M-v2 storage_epoch=2`; the
  bootloader lists the PT-4M-v2 table (`nvs`, `phy_init`, `otadata`
  0x10000, `rlcfg` 0x12000, `rlkeys` 0x18000, `rlsec` 0x20000, `ota_0`
  0x40000, `ota_1` 0x210000, `coredump` 0x3e0000).
- App-only rewrite keeps the NVS partitions: SHA-256 of `rlcfg`, `rlkeys`
  and `rlsec` read in ROM mode right before and right after the ota_0 write
  matched in **8/8** checked writes (DevRam 3, Member 3, role swap 2;
  `provision-*/…/provision.json`, `nvs_preserved`). The other app-only
  image swaps during the round were not hash-checked but every one booted
  with its committed board config. The field boot then
  reported the committed board config (`board config: gen=1 node=0x3
  secrets_gen=1 mac=10bda3b14754`, etc.).
- Wrong partition table: a table identical to PT-4M-v2 except
  `coredump` 0x8000 bytes (valid MD5, SHA-256 `b7514dec…`) was written to
  the endpoint. The app logged `partition coredump: … table is not PT-4M-v2
  (erase flash and write full image); RF not started`, never started Wi-Fi,
  and entered the fail back-off; the original table restored RF
  (`p01-negative-pt/`). **PASS.**
- App size vs `ota_0` (1,900,544 B, 80 % = 1,520,435 B): C3 bridge
  1,367,232 B (71.9 %), C3 reference 1,287,680 B (67.8 %), C6 reference
  ≤ 1,434,000 B (75.5 %), C6 bridge Member 1,501,952 B (79.0 %). **PASS**
  (the experimental C6 bridge is within 1 % of the limit).
- Rollback with a hand-made bad candidate: `NOT_RUN` — the app-side
  rollback confirmation was removed until the OTA path exists (#171).
- Flash smaller than 4 MB: `NOT_RUN` — no such board.

## Findings

- **F1 C6 Member maintenance console panics** (fix spec S1). On both C6
  boards (reference and bridge setup images) the `identity <bundle>` seal
  commits, then the console task `rl_maint` dies with `Guru Meditation
  Error: … (Stack protection fault)` before replying; `status` on a sealed
  identity panics the same way on every retry. `lock` and the console
  read-back cannot be done on C6. The C3 setup images completed status →
  keygen → seal → lock → status normally.
- **F2 Unconfigured board with a field image falls into a 30-minute sleep**
  (S2). The boot logs `E RouteLoomNVS: open rlcfg/board native=0x1102` and
  `fatal: nvs_open sdkv1 failed`, not `CONFIG_REQUIRED`, and the fail
  back-off ends in 30-minute deep sleeps with USB absent. `docs/hil.md`
  "Flash layout PT-4M-v2" step 2 tells the operator to full-flash a
  PT-4M-v2 image and provision afterwards, which leads straight into this.
- **F3 Relay reset recovery ~29 s** (S3): the downstream endpoint accepts
  the rebooted relay only after its own stale detection.
- **F4 Slow and variable convergence** (S4): cold start up to 38.5 s; the
  rebooted endpoint needed 22.8 s to reach a gateway route although its
  neighbour Node2 was bound at 1.6 s.
- **F5 P6 distribution silent** (S5): RRS1 epoch 2 applied 0/2 and cutover
  PREPARED 0/2, including the gateway on USB.
- **F6 Member wake delivers nothing** (S6): 0/3 first deliveries after
  warm restore.
- **F7 Non-terminal delivery states never end** (S7): five back-to-back
  `send`s to a member leave four requests at `TX_MAC_PENDING`/`QUEUED`
  for > 75 s while the receiver logged all five messages; spaced 1 s the
  same sends all end `delivered`. Seen twice on the C6 gateway (role swap)
  and as 1/6 still `TX_MAC_PENDING` after 4 s on the C3 gateway.
- **F8 Gateway idempotency bound**: the first reset-matrix run hit
  `IDEMPOTENCY_FULL` after ~112 legacy sends in one gateway boot (17
  refusals in the endpoint run, then all 100 sends of the following relay
  run); the table then refuses every new send until the gateway reboots. The run was repeated with a
  gateway reboot per role (`devram/m06-invalid-idempotency/` keeps the
  invalid run).
- **F9 C6 USB Serial/JTAG drops after an esptool session**: several times
  the C6 USB link disconnected and re-enumerated right after the app
  started following an esptool download-mode session, breaking open serial
  handles (`reset_cycles.py` crashed with `EIO` twice). It never happened
  on the C3. Treated as a bench/tool effect; `reset_cycles.py` now waits
  after the preflight reset and the capture helper reopens the port.
- **F10 Mesh Lab headless provisioning cannot complete** (S10):
  `LabProvisionBackend` passes the lab-site spec to `provision-devcert`,
  which requires `routeloom-identity-spec-v1`, and it resolves only
  `bench_node` bundles, which `build_bundle.sh` refuses to build.

### Recheck details

**F2** (`recheck/f2-unconfigured/`). `flash.py` without the flag stops
before any write with `rlcfg is blank: flash the setup image and commit the
BoardConfig first`; it used to print a Python traceback, and this PR makes
the CLI print `flash refused: …` and exit 4. The forced field image logs
`E RouteLoomRef: CONFIG_REQUIRED: board configuration required` from
609 ms and every 10 s; the by-id port was sampled every second for 630 s and
never disappeared; `nvs_open sdkv1 failed` 0 times. The setup image was then
written by the normal full-flash path.

**F1** (`recheck/f1-c6-console/`). Each cycle: full erase, setup image
`h0r-setup-ref-c6-member`, RLC1 BoardConfig (member), `Provisioner.run`
(status, keygen, office DevCert, identity seal, lock), three `status`, EN
reset, `status`. `console stack free=` per verb: status 9,024 B,
keygen 8,292–8,308 B, identity/lock/status 8,164–8,180 B.

**F10** (`recheck/f10-headless/`). `python -m routeloom_meshviz.provisioning
provision --role bridge` on the C3: the journal
(`bridge-journal.json`) has `setup_image`, `board_config`, `status`,
`keygen`, `issued`, `sealed`, `locked`, `field`, then the readback step
fails. The field boot capture of a bridge contains only ROM and bootloader
text because the bridge application console is UART0 (not wired on the
bench); the identity, `routeloom field boot` and `board config` lines never
reach USB. The module also needs a Python that imports `esptool`
(`No module named 'esptool'` with the system Python; it ran with esptool's
own virtualenv). The Member bridge was therefore finished from this
journal and joined normally.

**N1** (`recheck/bridge-bootloop/`). The first recheck images kept the
first run's `CONFIG_ROUTELOOM_CAPABILITY=0x867` for heap observation.
Since #212 the C3 bridge uses the `gateway_small` resource profile, whose
`CONFIG_ROUTELOOM_USB_NODE_STATUS` defaults to `n`; bit 0x40 still reaches
`attach_node_status()`, which answers `node status compiled out`, and the
bridge treats that as fatal. A USB-console diagnostic image showed the
line and `streak=10, deep sleep 1800000 ms`. The Kconfig help says bit 6
"is never advertised" when node status is off, but nothing masks or
rejects it. The run continued with `CONFIG_ROUTELOOM_USB_NODE_STATUS=y`
images (`h0r-bridge-c3-*-ns`), which `route_convergence.py` and `nodes`
need anyway.

**M06 relay** (`recheck/devram/m06-reset-relay/`, forced chain
1—2—3). After each relay reset one neighbour binds in 1.2–1.9 s and the
other at 14.9–32.3 s; this time the late one was the gateway in 7 cycles
and the endpoint in 2, and in cycle 4 the gateway never re-bound within the
cycle. Same mechanism as F3 (the far side keeps the old link until stale
detection), now seen on both neighbours.

**J01 / GK** (`recheck/member/`). The relay's stuck link to the gateway
cleared only with a gateway reboot (route after 9.9 s). The GK rotate
target that never acked is the gateway: both C6 members reported `gk=2`
at their next boot while the operation still counted one unknown target.

**J09** (`recheck/member/cutover-timeline.json`). The Owner prepared both
targets in 4 s, but the commit waited for the 10-minute prepare window to
expire and the apply then went through `recovery_pending`.
