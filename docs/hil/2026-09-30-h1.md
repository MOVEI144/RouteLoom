### Remote config (`member/p03-remote-config/`)

Bridge `h1-br-cfg-ns` (gateway + config endpoint, cap 0x5f); relay and
endpoint with `CONFIG_ROUTELOOM_CONFIG=y`. The daemon signs the permits
with the site SAK. SDK namespace 1, schema 1, field 1
(`diagnostics_level`, u8). Principal ACL needed `CONFIG`.

| Target | Update | Result | submit → `ACTIVE` | Readback | After target reset |
|---|---|---|---:|---|---|

| endpoint Node3 | rev 1 → 2 (level 1) | `ACTIVE` | 0.64 s | rev 2, hash equal | rev 2, same hash (new boot id) |
| relay Node2 | rev 0 → 1 (level 2) | `ACTIVE` | 0.65 s | rev 1, hash equal | rev 1, same hash (new boot id) |

- A propose with an empty base against revision 1 was `REFUSED/STALE`
  (compare-and-swap works). A propose with the wrong field type
  (`1:bytes:0002`) did not change the revision, but the host reported
  `INDETERMINATE` instead of a refusal (S6).
- The applied level took effect: the endpoint at level 1 logs only
  warnings afterwards.
- The E2E criterion "not `APPLIED` before the app completes after 2 s"
  needs the app provider of V2-14; the SDK field applies immediately, so
  that part is `NOT_RUN`.

### Explicit gateway (`member/p03-explicit-gateway/`)

No firmware app used `Device::gateway()`, so this PR adds a HIL-only sender
to `reference_node` (`CONFIG_ROUTELOOM_HIL_GATEWAY_SEND_COUNT`, default 0).
The relay resolved gateway Node1 (GATEWAY_SDK_RAM) and sent 20 messages,
one every 3 s:

- resolve: 5/5 Ready, 47–50 ms each; the descriptor lease is ~12 s, so the
  sender re-resolved after every four sends (`ENDPOINT_LEASE_TOO_SHORT`).
- sends 1–8 and 20: `ENDPOINT_RECEIVED`, 42–55 ms. Sends 9–19:
  `REJECTED`, reason 4 (CAPACITY). The USB bridge app never takes entries
  out of the GATEWAY_SDK_RAM mailbox, so after eight receipts it refuses
  until entries age out (S3). The refusal is honest; nothing claimed
  success without a receipt.
- The negative resolve of a non-gateway node could not be judged: the
  endpoint was isolated by S2 at the time, so the relay's resolve of Node3
  ended `NO_ROUTE`. A first attempt with a sender that read
  `send_result()` after completion logged `SEND_NOT_FOUND` for every send
  (the record is released after the observer callback); it is kept in
  `member/feat/` and not counted.

### Manual channel plan (`member/p03-channel-plan/`)

Bridge `h1-br-plan-ns` (cap 0x2047), members with `MIGRATION=2`. Host:
`site channel-plan status/offer/release` (the desk takes one request at a
time; an offer sent right after a status poll is refused `BUSY`, the first
attempt is kept in `attempt1-busy/`).

- 6 → 1: offer accepted (ledger 1); READY 2/2 at 5.0 s; release; the
  gateway reported channel 1, epoch 1 at 33.1 s. Both members logged
  `PHASE_SWITCHING`, `VERIFY_PASSED peer=1`, `PHASE_STABLE` 30 s after the
  offer; only the relay logged `radio generation now 1`. The 40 sends that
  followed: **Node3 0/20, Node2 1/20** (39 `HOP_ACCEPT_TIMEOUT`). The
  relay's ESP-NOW `send_failures` rose from 5,213 to 5,639 within three
  minutes, the endpoint marked peers 2 and 1 `STALE` 26 s and 52 s after
  the switch and kept logging `ESPNOW: Peer exists`. Node3 was still
  unreachable nine minutes later; Node2 delivered one probe of two.
- 1 → 6 after the 10-minute cooldown: the script released on the first
  report after the offer, which still carried the previous plan's
  `ready=2`; the gateway accepted the release with READY 1 and switched to
  channel 6 at 33 s. Node2 recovered (8/20), Node3 stayed on channel 1.
- After all boards were rebooted with MIGRATION images the endpoint stayed
  isolated for more than 10 minutes (`DISCOVERY_FAILED`/`REDISCOVERY`
  only). With a MIGRATION=0 image it rejoined at once on the site channel 6
  (100/100 in `member/ab-os-obs-no-ns`).
- **FAIL**: the switch itself completes on all three boards, but the data
  plane does not survive it, the gateway releases on partial READY, and a
  member left behind never finds its way back (S2).

## Findings

Carried in `spec-v2-hfix-h1`:

- **S1** relay reset: one neighbour bound late (~24 s) every cycle; #167
  not fixed on hardware.
- **S2** manual channel plan: data plane dead after a verified switch;
  release accepted on partial READY; a member left on the old channel stays
  isolated across reboots.
- **S3** explicit gateway GATEWAY_SDK_RAM on the USB bridge: mailbox never
  drained, CAPACITY after eight receipts; descriptor lease ~12 s.
- **S4** gateway idempotency bound 112 per boot (H0 F8), still present.
- **S5** a send left `queued` (H0 F7), still present.
- **S6** remote config wrong-type propose ends `INDETERMINATE`.
- **S7** C6 relay image with remote config + migration: heap largest
  block 14,336 B and no discovery for 5+ minutes after one all-board reset
  (seen once).

Bench-only observations: the C6 USB link dropped once more right after an
esptool session (H0 F9); the first `benchcfg stage` on the endpoint
answered `invalid_argument` and passed on retry.

## Tool changes in this PR

- `firmware/reference_node`: HIL-only explicit gateway sender
  (`CONFIG_ROUTELOOM_HIL_GATEWAY_SEND_COUNT`, `_GATEWAY_ID`,
  `_GATEWAY_WRONG`; default 0, product images unchanged). It resolves the
  named gateway through `Device::gateway()`, sends one message every 3 s,
  logs each terminal state from the delivery observer, re-resolves when the
  lease is too short, then resolves a node without a gateway role.
- `tools/meshviz/build_bundle.sh`: accept exactly
  `CONFIG_COMPILER_OPTIMIZATION_DEBUG=y`, so the `-Og` side of the A/B can
  be built as a signed bundle.
