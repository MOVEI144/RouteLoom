### 2. 多段（Issue #169）

Node3 は試験途中に復旧し、直後に bridge と直接 BIND/REACHABLE、host `nodes` は一時 `hops=1`、RSSI -33 dBm を報告した。その約 82 秒後に bridge は Node3 を STALE/REDISCOVERY、後続 snapshot で `connected=false` とした。[bridge→Node3 の 1 回確認送信](../../artifacts/hil/2026-09-26-full/c3-node3-recovered-smoke.jsonl) は `NO_ROUTE→DEADLINE_EXPIRED` で **0/1**。Node3 と Node2 も BOUND の約 30 秒後に STALE となり、双方の [Node3 console](../../artifacts/hil/2026-09-26-full/c3-node3-recovered-reset-console.log)・[Node2 console](../../artifacts/hil/2026-09-26-full/c3-only-node2-console.log) と [bridge events](../../artifacts/hil/2026-09-26-full/c3-node3-recovered-events.json) に残る。`PEER_CAPACITY` と `SEQNO_REQUEST_NO_PATH` もあるが、これだけで単一の原因には絞れない。C3 Node2 宛 campaign はその間も継続配達している。指定の C3 `1→2→3` を強制するための opt-in MAC 受信制限 image を build 中で、配送成功率・原因確定・修正判定は保留する。

C6 Node5 が先に Node4 と BOUND し、bridge→Node5 の 5/5 が届いたので、4 台構成の経路学習には成功例がある。ただし RF の遮断や近隣制限を用いて 2 hop を強制した証明ではない。

5 台同時 reset では bridge の経路が 120 秒間 0 件という障害を再現した。bridge だけを後で再起動すると Node3 が直接、Node2 が Node3 経由の metric 2 となり、Node2 宛 1+10+20 回が全件 END_RECEIVED。これは C3 の **1→3→2** の 2 hop 実例で、gateway の起動順／再起動が経路形成に影響した証拠である。指定の **1→2→3** は opt-in MAC 受信制限で強制して別途検証する。bridge が最初の同時起動でなぜ 0 経路になったかは未特定。

長時間 run の準備で Node2/4/5 を heap 計測 image に更新すると、bridge は Node2 を direct、Node5 を Node2 経由で学習した一方、Node3 は Node2 に BOUND しても REACHABLE に進まず、Node2 も Node3 に REDISCOVERY/STALE/PEER_CAPACITY を反復した（[Node2](../../artifacts/hil/2026-09-26-full/five-longrun-node2-console.log)、[Node3](../../artifacts/hil/2026-09-26-full/five-longrun-node3-after-reset-console.log)）。[bridge→Node3 送信](../../artifacts/hil/2026-09-26-full/five-longrun/traffic-100.jsonl) は `DEADLINE_EXPIRED`。MeshNode は discovery が REACHABLE とした peer だけを routing neighbor に載せるため、この観測だけでは「REACHABLE な Node3 の route advertisement が bridge に届かない」という #169 の経路伝播不具合とは確定できない。C6 を隔離し、MAC 受信制限で C3 の指定鎖を作って原因を分ける。

既存 host `test_routing_sims.cpp` には、relay と member が先に接続し、後で gateway が relay につながる 2 hop／3 hop の下り試験が flat/scoped 双方である。今回の GCC ASan ctest でも合格した。実機の BIND、無線近隣と host bridge を含まないため、Issue #169 の C3 実機再現を代替しない。

C6 Node4/5 を channel 11 に隔離し、C3 bridge は Node3 の MAC、C3 Node3 は bridge の MAC を HIL 設定で受信拒否して **1→2→3** のみ成立する形にした（Node2 は受信制限なし）。最初の強制鎖 image では bridge の Node3 経路が起動後 48.433 秒で `next_hop=2, metric=2` になったものの短時間で消え、[300 秒・5 秒間隔の監視](../../artifacts/hil/2026-09-26-full/c3-chain/unstable-routes-5s.jsonl)は Node3 `connected=false` **60/60**、[最初の 3 送信](../../artifacts/hil/2026-09-26-full/c3-chain/initial-node3-3.jsonl)は **0/3** `DEADLINE_EXPIRED`。C3 の実機だけで BIND 後の bridge `NO_ROUTE` を再現した。

追加の [Node2](../../artifacts/hil/2026-09-26-full/c3-chain/diag-node2-console.log)・[Node3](../../artifacts/hil/2026-09-26-full/c3-chain/diag-node3-console.log) 診断では双方の Probe/Result が RF 到達し、Node3 は Result を受信していた。Node3 は Node2 からの経路更新で初期に `ROUTE_UPDATE_REJECTED` を 2 件出したが、これは `Withdrawn` も同じ診断名にまとめるため拒否理由と destination の同定には足りない。世代番号が下の認証済み Probe を無応答で捨て、相手を再試行に閉じ込める別の欠陥を host 回帰試験で再現した。[修正](../../components/routeloom/src/discovery.cpp)では古い Probe で lease を延長せず、現行世代を Result で返す。対象 ASan 試験は修正前に失敗、修正後に合格。これが今回の全不達の唯一の原因とはまだ言えない。

再起動後の診断 image では [Node3 起動ログ](../../artifacts/hil/2026-09-26-full/c3-chain-r4-flash-node3/flash-ref-b-boot.log) に Node2 `REACHABLE` と bridge 宛 `via=2, metric=2`、[Node2 起動ログ](../../artifacts/hil/2026-09-26-full/c3-chain-r4-flash-node2/flash-ref-a-boot.log) に bridge と Node3 の両方が `REACHABLE`、双方の直接経路 metric 1 を記録した。bridge host の `nodes` も Node3 を `next_hop=2, metric=2` と表示し、[bridge→Node3 の最初の 3 回](../../artifacts/hil/2026-09-26-full/c3-chain/r4-node3-traffic-3.jsonl)は **3/3 END_RECEIVED**、host 受理→terminal 観測は中央値 157.60 ms、最大 311.44 ms。

[両端が連続 capture できた 2,377 秒](../../artifacts/hil/2026-09-26-full/c3-chain/r4-data-trace-pair-long.json)の relay Node2→Node3 DATA frame（type 16）は送信 79 unique、受信 79 unique、重複・片側だけの sequence は 0。これはこの区間のログで照合可能な 1 hop frame の観測損失 0/79 であり、無線 sniffer による再送を含む空中 packet loss ではない。再 flash・再起動も同時に行ったため、Probe 修正単独の因果効果とは判定しない。

### 3. reset／4. 長時間／5. deep sleep／6. MemberEdhoc／7. 性能／8. 無線

C3 強制 1→2→3 の安定 100 回の直後、bridge Node1 だけを chip/MAC/security preflight で毎回 hard reset し、host daemon を再接続して Node3 宛 10 件を送る試験を **10 cycle×10 送信**実施した（[全 cycle の preflight・送信・daemon log](../../artifacts/hil/2026-09-26-full/c3-reset-bridge-10x10/)、[集計](../../artifacts/hil/2026-09-26-full/c3-reset-bridge-10x10/summary.json)）。各 cycle の USB 認証時間は 1.506〜1.531 秒、中央値 1.517 秒。配送は順に **0,0,0,10,10,10,0,0,0,0 /10、計 30/100 で不合格**。70 件すべて `DEADLINE_EXPIRED`、成功 30 件は `END_RECEIVED`、admission retry 0。bridge message session は cycle 間で 251→267 と後退しなかったが、永続 counter 値の直接読出しは未実施。失敗側の [Node2/3 console](../../artifacts/hil/2026-09-26-full/c3-reset-bridge-10x10/)では Node3 の gateway 経路が無効で、Node2 の bridge 宛 Probe Result 送信が `status=3`（`NotFound`）を多数返した。telemetry の当時の log は detail を出さないため、discovery mapping 不在か ESP-NOW driver peer 不在かは未確定。`ROUTE_UPDATE_REJECTED` は撤回通知でも出るため単独原因とはしない。bridge 既定 console は UART0 未配線で、bridge の起動 heap を直接読めない。

同じ C3 強制鎖を 3 台同時に hard reset した第 1 試行は、全 3 台が USB ONLINE、release skew 0.369 ms（[reset](../../artifacts/hil/2026-09-26-full/c3-simultaneous-reset/result.json)）。reset release から約 12.1 秒後の最初の host 観測で Node2 direct、Node3 via Node2 metric 2 の **2/2 経路**。この観測値は収束時間の上限であり正確な初回到達時刻ではない。[交互 20 送信](../../artifacts/hil/2026-09-26-full/c3-simultaneous-reset/traffic-20.jsonl)は Node2 **10/10**、Node3 **10/10**、計 **20/20 END_RECEIVED**、受理→terminal 遅延中央値 113.35 ms、p95 229.84 ms、最大 333.10 ms、admission retry 12、総計 120.21 秒。

第 2 同時 reset は USB **3/3 ONLINE**、release skew 0.440 ms だが、[host 監視](../../artifacts/hil/2026-09-26-full/c3-reset-endpoint-prep-node2-retry/routes.jsonl)に先立つ最初の観測から Node2/3 経路 0/2。Node2 単独 reset 後もさらに 90 秒、経路 0/2 のまま。端末には相互の RLD1 と `REDISCOVERY` が繰り返され、ESP-NOW の `Peer exists` 警告も出た（[Node2](../../artifacts/hil/2026-09-26-full/c3-reset-endpoint-prep-node2.log)、[Node3](../../artifacts/hil/2026-09-26-full/c3-reset-endpoint-prep-node3.log)）。第 3 同時 reset は USB 3/3 ONLINE、release skew 0.327 ms、[30 秒の監視](../../artifacts/hil/2026-09-26-full/c3-reset-endpoint-prep2/routes.summary.json)で Node2 経路のみ、Node3 未到達。したがって C3 だけでも reset 復旧は再現性がなく、1 回目の 20/20 を一般化しない。端末・relay 個別 10×10 は安定 baseline を再確保してから実施する。

診断 image を全 C3 に更新しても、修正前は [Node2](../../artifacts/hil/2026-09-26-full/c3-chain-r5-node2-console.log) が Probe 応答で `ESP-NOW peer not found` を 1,031 回、[Node3](../../artifacts/hil/2026-09-26-full/c3-chain-r5-node3-console.log) が 4,036 回記録し、[90 秒の host 経路](../../artifacts/hil/2026-09-26-full/c3-chain-r5-routes.summary.json)は 0/2 だった。両端の software discovery は peer を `REACHABLE` として扱う時間がある一方、ESP-NOW driver は同じ MAC の peer が見つからない。通常 peer と一時 peer が同じ MAC の物理登録を共有した後、一時 slot の清算が `esp_now_del_peer()` を呼べる実装だった。通常 peer の `driver_registered` が true なら一時 slot だけを消すよう修正し、[ESP runtime 回帰試験](../../artifacts/hil/2026-09-26-full/c3-chain/transient-regression-before.log)は修正前に物理 peer 削除を検出して失敗、[修正後](../../artifacts/hil/2026-09-26-full/c3-chain/transient-regression-after.log)に合格した。修正 image の C3 bridge/Node2/Node3 を chip/MAC/security preflight 後に書き込み、bridge reset 後の最初の host 観測では Node2 direct、Node3 via Node2 metric 2 の [2/2 経路](../../artifacts/hil/2026-09-26-full/c3-chain-r6-routes.summary.json)が戻った。この 1 回だけで reset 耐久性を合格とはせず、端末 10×10 と再度 bridge 10×10 を実施する。

未収束の原因候補として、DevRam の [SecurityCoordinator `on_poll()`](../../components/routeloom/src/sdkv1_security_coordinator.cpp) は採用後に `StartMemberDiscovery` を 1 回出し、[ESP-NOW Owner](../../components/routeloom_espnow/src/espnow_security_owner.cpp) が初回 `begin_discovery()` を呼ぶ。[失敗後の discovery `poll()`](../../components/routeloom/src/discovery.cpp) は stale 近隣の再発見だけを起動する。bridge が初回交換で近隣 0 のまま失敗すると、同じ boot の再試行がないように見える。bridge 側 console は USB protocol と分離した UART0 にあり、この run で `DISCOVERY_FAILED` を直接採取できていないため、仮説を確定原因とはしない。復旧政策は無線負荷・sleep 予算にも関わる設計変更なので、本 HIL branch では推測だけで書き換えない。

### MemberEdhoc：C3 だけの cutover と起動障害

同じ fresh Site で epoch 2 の SiteCert を発行し、epoch 1→2 cutover を操作 `op-0000000000000005` として開始した。対象は Node1 gateway、Node2 relay、物理 Node3 を NodeId 6 とした endpoint の **C3 3 台**。作成時は `preparing`、PREPARED 1/3。開始後約 6 分時点でも 1/3 だったため、Node2/6 を各 1 回、chip/MAC 照合付き `esptool chip-id` で reset した（[Node2](../../artifacts/hil/2026-09-26-full/r2/node2-cutover-preflight-reset.log)、[Node6](../../artifacts/hil/2026-09-26-full/r2/node6-cutover-preflight-reset.log)）。約 370 秒時点で 2/3、Node6 を約 520 秒時点でもう 1 回 [照合付き reset](../../artifacts/hil/2026-09-26-full/r2/node6-cutover-second-preflight-reset.log)。期限 600 秒では 2/3 で、operation は `waiting_gateway`。[10 秒時系列](../../artifacts/hil/2026-09-26-full/r2/newsite-cutover-observe.jsonl)と[端末 console](../../artifacts/hil/2026-09-26-full/r2/node6-cutover-after-reset-console.log)を保存した。

観測中、17:09:40 UTC 頃に bridge USB ポートを console 用に開いてしまい Node1 が reset された。rig 定義の「bridge USB を console 捕捉しない」に反する測定操作であり、その時刻の連続性と USB protocol error は**本試験側が汚染**した。すぐ捕捉を停止し、daemon の再接続・Node1 authority channel 再確立を確認した（[host event](../../artifacts/hil/2026-09-26-full/r2/newsite-cutover-final-events.json)）。この操作を cutover 障害の原因と断定しない。600 秒を過ぎても gateway の PREPARED がなかったため、Node1 を [chip/MAC 照合付きで明示的に reset](../../artifacts/hil/2026-09-26-full/r2/node1-cutover-waiting-gateway-preflight-reset.log)。これで PREPARED は **3/3** となり、[秘密を除いた台帳 target](../../artifacts/hil/2026-09-26-full/r2/newsite-cutover-targets-redacted.json)も Node1/2/6 全員を `prepared` と記録した。gateway が初期に ACK しなかった理由は未特定。

[host event](../../artifacts/hil/2026-09-26-full/r2/newsite-cutover-final-events.json)では `waiting_gateway` が Unix ms **1790442679596**、台帳 `committed` が **1790442761081**、60 秒後の `recovery_pending` が **1790442821104**。commit は開始から約 **681.6 秒**、RS 1→2、GK 2→3、network `00000002524c0003`。しかし [最終観測](../../artifacts/hil/2026-09-26-full/r2/newsite-cutover-postdeadline-observe.jsonl)は PREPARED **3/3**、Site が確認した APPLIED ACK **0/3**、全員 `allowed_unconfirmed`、authority channel **0**。gateway は commit 後に USB 接続を失い、serial には再接続するが認証できない。Node2/6 宛の [送信 2 件](../../artifacts/hil/2026-09-26-full/r2/newsite-postcutover-send-2.json)はともに `session not authenticated` で受理 0/2。**新 epoch 通信の合格証拠はない**。旧 5 台 Site の cutover と同じく、台帳 commit と機器適用は異なる。

daemon を停止した後の Node1 USB [boot log](../../artifacts/hil/2026-09-26-full/r2/node1-postcutover-no-dtr.log)では `RTC_SW_CPU_RST` と同じ `Saved PC:0x40388246` が約 **1.5 秒**ごとに繰り返され、アプリ起動完了には至らない。bridge image のアプリログは UART0 で、この bench に配線されていないため `fail()` の文字列は取得できず、再起動原因はこの log だけでは未特定。現場 `rlsec` は[私有 backup と hash](../../artifacts/hil/2026-09-26-full/r2/node1-postcutover-rlsec-sha256.txt)を作成し、消去せずに DevRam 保守 console を [app-only flash](../../artifacts/hil/2026-09-26-full/r2/node1-postcutover-console-flash/flash-bridge.json)。[console status](../../artifacts/hil/2026-09-26-full/r2/node1-postcutover-maintenance-status.log) は `identity=sealed pending=0`。

ESP-IDF v6.0.3 の NVS parser を **repo 外の private backup だけ**に適用し、秘密・証明書・GK を出力せず [slot metadata](../../artifacts/hil/2026-09-26-full/r2/postcutover-nvs-metadata-redacted.json)を残した。Node1 の `rlsite` 双子スロットは CRC 有効・同一 sequence 6 で **epoch 2 / RS floor 2 / GK 3**、lifecycle journal 双子は `Idle` / epoch 2。よって Node1 は**ローカル永続状態まで**新 epoch を適用したが、この時点では起動ループで Site へ APPLIED ACK を送れず、新 epoch 通信もできなかった。Node2 は `rlsite` epoch 1 / GK 2、journal `Prepared`、Node6 も epoch 1 / GK 2、journal `Prepared`。両端は COMMIT を適用していない。この読取りは上記ホストの ACK 0/3 と矛盾せず、ACK 0 をローカル適用 0 と読み替えない。Node1 の default NVS `rlboot.session` は読取り時 **533** で `rlsite.boot_witness` **357** より進んでおり、少なくとも数値上の単純な後退ではない。この時点では起動ループの原因と counter 予約境界の単調性は未確認だった。C3/C6 混在 5 台の結論として外挿しない。

起動原因を読むため、Node1 の site/identity を消さずに ESP-IDF `CONFIG_ESP_CONSOLE_USB_SERIAL_JTAG=y` の診断 bridge image を app-only flash した。chip/MAC/security の事前照合は [manifest](../../artifacts/hil/2026-09-26-full/r2/node1-postcutover-usbdiag-flash/flash-bridge.json)。[USB アプリ log](../../artifacts/hil/2026-09-26-full/r2/node1-postcutover-usbdiag-flash/flash-bridge-boot.log)は、新 epoch `0x2524c0003` の site と `Idle` journal を読み、`booted (usb-direct)` 後に毎回 `p6: adopting network ... rebooting` を実行することを直接示した。`MembershipLifecycle::on_boot` は `Idle` から `AdoptNetwork` を出し、ESP Owner は実行中の cutover 用 action と区別せず再起動する。よって **新 site の再採用を完了できない無限再起動**が直接原因。先の約 1.5 秒周期はこの意図した reboot だった。

### 原因の切り分けと残る設計判断

現行 source の [`tick_cutover`](../../host/routeloom-host/src/site/cutover.rs) は commit 後 **60 秒**のみ `COMMIT` を queue し、期限後は `recovery_pending` に移る。`queue_grants` は target list 順であり、R2 の [赤字除去済み target](../../artifacts/hil/2026-09-26-full/r2/newsite-cutover-targets-redacted.json)は Node1 gateway、Node2 relay、Node6 endpoint の順。配布には 100 ms の間隔がある。Node1 が最初に COMMIT を受けて旧 network を退役すると、後続宛先への旧ネットワーク配送が途切れる可能性がある。ただし P6 から無線への各 COMMIT の到達順・端末の受理時刻は今回の log にないため、この順番が実際の失敗原因と**確定はしない**。

一方、端末側の [`on_boot`／`on_link_failure`／`on_recovery`](../../components/routeloom/src/sdkv1_revocation.cpp) は journal `Prepared` から旧 site を再採用し、link failure で recovery を始める条件は `Active` のみ、recovery 完了入力は `Prepared` を拒否する。host の grace が失効した後、R3 のように旧 epoch で互いに link が 1 本残る端末を新 Site へ戻す自律経路は、この条件では確認できない。署名済み COMMIT の再配送、旧／新ネットワークの移行順序、`Prepared` からの認証済み ZeroTouch reissue と journal の処理を合わせて設計する必要がある。今夜は未検証の配布順だけを変える修正や旧 journal を消す操作を行わず、**cutover は不合格**のまま残す。full 64-bit の group 拒否は [`parse_network_hex`](../../host/routeloom-host/src/acl.rs) の wire-v1 上限 `0xffffffff` で再現し、Site の 64-bit epoch と API1 の適用範囲を決める必要がある。
