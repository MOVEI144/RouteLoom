# RouteLoom SDK v1 実機検証（2026-09-26 JST、R3 継続）

## 残項目と次の手順

1. **5 台 DevRam mesh**: Node3 の C3 が USB に再列挙されず、現物は 4 台のみ使用可能。USB と電源を現場で点検し、chip-id/MAC を再照合してから Node3 を書き込み、5 台の経路と配送を再試験する。C5 は 0 台なので C3/C5 実機比較には C5 を別途用意する。
2. **reset 後の復旧**: R2 の C6 receiver reset 後 60 秒 0/10、全台 reset 失敗に続き、R3 の C3 receiver reset 後も 60 秒 0/16。hop accept までは進むが end receipt が戻らない。両端の session/replay/route/receipt 状態を同時採取し、突然の電源断後の再 handshake と counter 非後退を検証する。
3. **deep sleep の残範囲**: R3 で LegacyFixture C3 の予定 sleep→timer wake→配送を 1 cycle 合格にした。DevRam/MemberEdhoc の RTC counter 先行更新と sleep image 復元、経過時間の信頼できる上限は未証明。これらを別途実機で検証する。
4. **Site Authority 完了**: R1 で P7、ZeroTouch、承認、GK readback、member 配送まで確認した。R3 で再開した Node4 は unicast が届く一方、authority carrier 5 件を mesh に queue しても Site に届かず、JoinConfirm/GK ACK は未達。reference の authority 送信 job と bridge の受信を同時に trace し、送出失敗か demux 失敗かを確定してから revoke 後の実機締め出し、手動 GK 更新、cutover を行う。
5. **残る実測**: 指定 2～3 hop の強制と経路表収束、100 回の無線配送成功率、group-send の DevRam 対応、EDHOC の個別 crypto 時間と peak heap、C5 実機、LR250 の air rate と独立した損失率を測る。

R1 の全手順と証跡は [R1 時点の報告](2026-09-26-bench-5node-r1.md) に保存した。以下は R2 と R3 の累積判定である。C6 は **SDK v1 対象外の実験 target** であり、C6 の結果を C5 の代用として扱わない。

## R3: reset の切り分けと LegacyFixture deep sleep の修正

R2 の DevRam image を使い、bridge daemon を新規 socket で起動して送信した [開始時の 3 件](../../artifacts/hil/2026-09-26/r3/baseline-traffic.jsonl) は Node2 と Node5 が `END_RECEIVED`、Node4 は `NO_ROUTE`→`DEADLINE_EXPIRED` で **2/3**。受理→受領は 206.17 / 208.21 ms。Node4 の [serial](../../artifacts/hil/2026-09-26/r3/ref-c-baseline.log) には bridge peer=1 の `STALE` があった。これは R2 末の reset 不調が残る条件であり、5 台 mesh 成功とは扱わない。

C3 Node2 を chip/MAC preflight 後 RTS assert 5.019 秒で reset した [結果](../../artifacts/hil/2026-09-26/r3/reset-ref-a.json) は、assert 中 1 件が期限切れ、解除後 60 秒の 16 試行が **0 件 delivered**。12 件は `END_RECEIPT_TIMEOUT`、最後の 4 件は固定長の端末 idempotency table による `IDEMPOTENCY_FULL`。bridge の [event dump](../../artifacts/hil/2026-09-26/r3/bridge-events-after-reset.json) は `HOP_ACCEPT_PENDING`→`END_RECEIPT_PENDING`→timeout と、後半の peer=2 `STALE` を示す。Node2 の [serial](../../artifacts/hil/2026-09-26/r3/ref-a-after-reset.log) は peer=5 への `session unknown context` を多数記録したが、reset 直後の全区間を capture できていない。end receipt 不達の根本原因は確定せず、この reset 不具合には firmware 修正を加えていない。

C6 2 台を RTS assert のままにして C3 だけを分離する追加試行では、20 秒待った [基準送信](../../artifacts/hil/2026-09-26/r3/isolate-c3-reset-settled/baseline.jsonl) は 1/1 delivered、[C3 reset 後](../../artifacts/hil/2026-09-26/r3/isolate-c3-reset-settled/reset-ref-a.json) は 60 秒間 0/17（14 `HOP_ACCEPT_TIMEOUT`、2 `IDEMPOTENCY_FULL`、1 admission timeout）だった。ただし [event](../../artifacts/hil/2026-09-26/r3/isolate-c3-reset-settled/events.json) は RTS assert から約 45.5 秒後に C6 peer=5 の `BOUND` と `REACHABLE` を示す。USB Serial/JTAG の RTS はこの条件で C6 を継続的に停止できなかったため、**C3 だけの隔離試験としては無効**。reset 後失敗の追加観測としてのみ扱う。

R2 の clean LegacyFixture では予定 sleep 後に `replayed security counter` で配送できなかった。RX replay guard は crash 時の再受理を防ぐため、最後の受信 counter より先まで永続上限を予約する。予定 sleep でこの上限を残すと、起きた受信側が peer の新しい frame まで拒否する。R3 では C3 LegacyFixture の sleep entry が radio/node を quiesce した後、cached RX window を `close_context` で最後の受信 counter に縮め、window cache を空にして、永続化失敗時は sleep entry を拒否する小修正を入れた。[reference image と構成](../../artifacts/hil/2026-09-26/images/ref-a-legacy-sleep-r3/) は ESP-IDF v6.0.3 で build した。bridge は R2 の [LegacyFixture image](../../artifacts/hil/2026-09-26/images/bridge-legacy-sleep-r2/) を使用した。

検証では両 C3 の rlsec を私有 mode 0700 directory に [bridge backup](../../artifacts/hil/2026-09-26/r3/bridge-rlsec-backup/manifest.json)、[reference backup](../../artifacts/hil/2026-09-26/r3/ref-a-rlsec-backup/manifest.json) し、partition のみ消去して flash した。最初の capture は `--reset-on-connect` が各 wake に USB reset をかけたため、deep sleep の証明から除外した。再試験はこの option を外した [連続 serial](../../artifacts/hil/2026-09-26/r3/ref-a-sleepfix-no-reset.log) で、`WAKE_DEEP_SLEEP`→`RESUME_CONFIRMED` と timer wake を確認した。同じ bridge boot/session 171 のまま、[sleep 前 sequence 5](../../artifacts/hil/2026-09-26/r3/sleepfix-awake-baseline.jsonl) と [wake 後 sequence 6](../../artifacts/hil/2026-09-26/r3/sleepfix-after-real-wake.jsonl) はどちらも `END_RECEIVED`、受理→受領 104.08 / 104.09 ms。reference の serial も両 message を記録し、この区間に replay 診断はない。**LegacyFixture C3 の予定 sleep 1 cycle で修正を実機確認した**。突然の reset、MemberEdhoc の RTC write-ahead と sleep image、信頼できる経過時間上限をこの結果から合格とはしない。

[GCC ctest](../../artifacts/hil/2026-09-26/r3/host-ctest.log) は 95/95 合格。修正を含む同じ LegacyFixture deep sleep 構成は C5 と S3 でも ESP-IDF v6.0.3 build が通り、静的 RAM の空きは C3 DRAM 102,566 B、[C5 HP SRAM 72,237 B](../../artifacts/hil/2026-09-26/images/ref-c5-legacy-sleep-r3/build/ram-report.json)、[S3 DIRAM 124,527 B](../../artifacts/hil/2026-09-26/images/ref-s3-legacy-sleep-r3/build/ram-report.json)。C5/S3 の値は build-only で、実機の睡眠・heap は未測定。試験後、bridge/ref-a を R2 の DevRam image に戻し、私有 backup の rlsec を chip/MAC 再照合後に書き戻して byte-for-byte readback で検証した（[bridge](../../artifacts/hil/2026-09-26/r3/restore-bridge-rlsec/manifest.json)、[reference](../../artifacts/hil/2026-09-26/r3/restore-ref-a-rlsec/manifest.json)）。backup の鍵素材は repository に置いていない。R3 で書いたのは chip/MAC 確認済み C3 の flash のみで、C6 は書き換えていない。eFuse 書込み、flash 暗号化・secure boot の有効化、sudo 操作はいずれも 0 件。

## R3: MemberEdhoc / Site Authority の再開と未達の切り分け

R1 の Site 台帳と秘密鍵は repository 外の mode 0700 私有ディレクトリにコピーした。両 C3 の DevRam `rlsec` を [bridge](../../artifacts/hil/2026-09-26/r3/member-switch-bridge-backup/manifest.json)、[ref-a](../../artifacts/hil/2026-09-26/r3/member-switch-ref-a-backup/manifest.json) に退避後、chip/MAC を照合して partition だけ消去した。現行 source の [MemberEdhoc bridge](../../artifacts/hil/2026-09-26/images/bridge-member-r3/) と [Node4 reference](../../artifacts/hil/2026-09-26/images/ref-a-node4-member-r3/) を build・flash し、R1 の identity/Site `rlsec` をそれぞれ [bridge](../../artifacts/hil/2026-09-26/r3/restore-bridge-member-rlsec/manifest.json)、[reference](../../artifacts/hil/2026-09-26/r3/restore-ref-a-member-rlsec/manifest.json) に示す通り byte-for-byte で復元した。秘密鍵と flash dump は commit していない。

Site Authority `--site-authority` と USB bridge daemon を起動すると、Node1 の authority channel は ready となり、Node1 の `authority.pull` は `answered`。[再開時の Site 状態](../../artifacts/hil/2026-09-26/r3/site-resume-status.json) は Node1 active、Node4 `allowed_unconfirmed`、GK epoch 2 `catching_up`、対象 2 台の ACK は 0/2 だった。Node4 の pairwise Link/End は各 1 session 確立し、[MemberEdhoc unicast](../../artifacts/hil/2026-09-26/r3/site-member-resume-traffic.jsonl) は 1/1 delivered（受理→受領 53.2 ms）。bridge の再 flash 後も [1/1 delivered](../../artifacts/hil/2026-09-26/r3/site-authorityfix-traffic.jsonl)（258.5 ms）、reference の追加計測 image 後も [1/1 delivered](../../artifacts/hil/2026-09-26/r3/site-jobdiag-traffic.jsonl)（104.48 ms）だった。これらは少数の smoke test であり、無線成功率とはしない。

一方、[reference の authority log](../../artifacts/hil/2026-09-26/r3/ref-a-jobdiag-site.log) は `tx_carrier=5 queued=5 shed=664`、`rx_carrier=0`、config job の hop accept/失敗 callback は 0/0。`shed` は起動直後、Link/End が使える前の繰り返しを含み、5 件は mesh queue へ受理された。Site の [event](../../artifacts/hil/2026-09-26/r3/site-jobdiag-events.json) は Node1 の Pull だけで、Node4 の authority event は 0。[bridge USB console の無 host 75 秒 capture](../../artifacts/hil/2026-09-26/r3/bridge-authdiag-nohost.log) では、同時期の reference `tx_sent=6` に対し relay `rx_carrier=0 rx_manifest=0 rx_chunk=0`。この capture は host を切った条件なので USB 上り配送の成否は測れないが、authority gateway の mesh intake に届かない事実は示す。原因は mesh queue 後から gateway intake までのどこかで、まだ特定できていない。

コード上は別に 2 点見つけた。remote config 有効 bridge では `attach_config()` が先に設定した authority sink を上書きするため、`ConfigGateway` が authority carrier を先に振り分けるようにした。ただし今回の bridge capability は `0x7` で config endpoint は無効なので、**今回の不達原因と断定しない**。また remote config 無効 reference は authority 受信 sink 自体を登録していなかったため、MemberEdhoc では単独 sink を登録するようにした。これは R2/JoinConfirm/GK 更新の下り受信に必要だが、修正後も上りが Site に届かず JoinConfirm は未達。gateway の demux 分岐は [host 回帰試験](../../artifacts/hil/2026-09-26/r3/host-ctest-final.log) 95/95 で確認し、修正を含む C3 実機 image、C5/S3 build-only image を作った。**authority 完了経路は合格扱いしない**。

最終 [Site 状態](../../artifacts/hil/2026-09-26/r3/site-jobdiag-status.json) は GK `catching_up`、ACK unknown 2、Node4 `allowed_unconfirmed` のまま。したがって Node4 revoke 後の物理的締め出し、追加 `group_keys.rotate`、cutover は再実行しなかった。R1 の Node2 revoke は Site commit と epoch 更新まで確認済みだが RemovalNotice 到達と旧 identity の実機拒否は未証明。

C5 の config 有効 MemberEdhoc bridge は通常 dedup で IDF build 自体は通ったが、[RAM guard は 5,971 B < 8,192 B で不合格](../../artifacts/hil/2026-09-26/images/bridge-c5-member-config-r3/build.log)。[leaf dedup image](../../artifacts/hil/2026-09-26/images/bridge-c5-member-config-leaf-r3/build/ram-report.json) は HP SRAM 空き 14,739 B で guard 合格。[C5 reference](../../artifacts/hil/2026-09-26/images/ref-c5-member-authoritysink-r3/build/ram-report.json) は 9,205 B、[S3 reference](../../artifacts/hil/2026-09-26/images/ref-s3-member-authoritysink-r3/build/ram-report.json) は 53,551 B の静的 RAM 空きで build が通った。いずれも実機性能・稼働の証拠ではない。

終了時には DevRam の partition table と firmware を両 C3 に再 flash し、私有 backup の `rlsec` を chip/MAC preflight 後に復元して readback 一致を確認した（[bridge](../../artifacts/hil/2026-09-26/r3/restore-devram-bridge-rlsec/manifest.json)、[reference](../../artifacts/hil/2026-09-26/r3/restore-devram-ref-a-rlsec/manifest.json)）。[最終 rig](../../artifacts/hil/2026-09-26/r3/rig-after-devram-restore.log) は Node1/2/4/5 ONLINE、Node3 OFFLINE。復元後の DevRam smoke test は [Node2](../../artifacts/hil/2026-09-26/r3/devram-restored-node2-acl.jsonl) 1/1、[Node5](../../artifacts/hil/2026-09-26/r3/devram-restored-node5-acl.jsonl) 1/1 delivered、[Node4](../../artifacts/hil/2026-09-26/r3/devram-restored-node4-acl.jsonl) は 0/1 `DEADLINE_EXPIRED`。daemon は停止した。Node4 の不調を含め、4 台 mesh の安定復旧とは判定しない。

## DevRam 4 台実験

最初の C6 build は component manifest の target 制限で止まった。esp32c6 を **実験用** target に追加した後、reference Node4/5 を IDF v6.0.3 で build し、chip/MAC preflight 後に flash した。[Node4 image](../../artifacts/hil/2026-09-26/images/ref-c-c6-devram/)、[Node5 image](../../artifacts/hil/2026-09-26/images/ref-d-c6-relayfix/)。C6 log は DevRam adoption と Node4↔5 BOUND/REACHABLE を示す。[Node4 boot](../../artifacts/hil/2026-09-26/r2/flash-ref-c/flash-ref-c-boot.log)、[Node5 boot](../../artifacts/hil/2026-09-26/r2/flash-ref-d-relayfix/flash-ref-d-boot.log)。

最初の 4 台送信はすべて NO_ROUTE→DEADLINE_EXPIRED。bridge に R1 の Site identity/GK が残っていたため、私有 backup 後に bridge と ref-a の rlsec を消去した。さらに relay Node5 で BOOTSTRAP_TRANSIT_ROLE を再現し、MemberConfig adoption 時に MeshNode の local role が更新されていないことを特定した。on_member_config で role を反映する小修正を行い、host ctest 95/95 と実機で再試験した。[修正後送信](../../artifacts/hil/2026-09-26/r2/send-relayfix.jsonl) は Node2、5、4、4、2 の 5/5 が delivered / END_RECEIVED。[Node2](../../artifacts/hil/2026-09-26/r2/capture-ref-a-relayfix.log)、[Node4](../../artifacts/hil/2026-09-26/r2/capture-ref-c-relayfix.log)、[Node5](../../artifacts/hil/2026-09-26/r2/capture-ref-d-relayfix.log) は message origin=1 を記録した。

## reset と deep sleep の再現

- [receiver reset](../../artifacts/hil/2026-09-26/r2/reset-receiver-c6/result.json): chip/MAC 照合済み C6 Node4 の RTS を 5.021 秒 assert。assert 中 1 件は DEADLINE_EXPIRED、解除後 60 秒の 10 件も全件 DEADLINE_EXPIRED。R3 で判明したように RTS assert は C6 の継続停止を証明しない。Node4、relay Node5 を個別に reset して BOUND を再観測しても Node4 宛は戻らなかった。
- [4 台同時 reset](../../artifacts/hil/2026-09-26/r2/reset-all-active/result.json): RTS assert skew 0.139 ms、release skew 34.96 ms、操作エラー 0。後続の Node2/5/4 宛 5 件は全件期限切れ。[直後](../../artifacts/hil/2026-09-26/r2/send-after-all-reset.jsonl)、[90 秒超の Node2](../../artifacts/hil/2026-09-26/r2/send-after-all-reset-late.json)。個別 bridge reset 後 Node4 は 2 回 delivered、Node2/5 は期限切れのまま。[再試行](../../artifacts/hil/2026-09-26/r2/send-after-bridge-individual-retry.json)。復旧は宛先依存で、全台復旧時間を報告できない。
- boot count は C6 Node4/5、C3 Node1/2 で増加したが、送受信 frame counter の単調性を読み出せず、counter 非後退は未証明。
- sleep は C3 bridge/reference を別 network の LegacyFixture 静的 peer とし、reference を 20 秒 awake / 10 秒 timer sleep に設定。[image](../../artifacts/hil/2026-09-26/images/ref-a-legacy-sleep-r2/)。最初は既存 state の影響を疑ったため、両 C3 の rlsec をさらに私有 backup 後に消去した。[bridge](../../artifacts/hil/2026-09-26/r2/bridge-rlsec-legacy-clean/manifest.json)、[ref-a](../../artifacts/hil/2026-09-26/r2/ref-a-rlsec-legacy-clean/manifest.json)。
- 新規状態の [sleep 前送信](../../artifacts/hil/2026-09-26/r2/legacy-sleep-clean-baseline.jsonl) は 1/1 delivered、約 103 ms。最初の [wake 後送信](../../artifacts/hil/2026-09-26/r2/legacy-sleep-clean-after-wake.jsonl) は HOP_ACCEPT_TIMEOUT。[serial](../../artifacts/hil/2026-09-26/r2/ref-a-legacy-sleep-clean-cycles.log) は WAKE_DEEP_SLEEP→RESUME_UNCONFIRMED と replayed security counter peer=1 を示す。bounded discovery と信頼できる経過時間上限は未実装で、warm restore/RTC counter 先行更新を合格としない。
- 試験後は chip/MAC を再照合して bridge/ref-a を DevRam image に戻した。[ref-a 復旧](../../artifacts/hil/2026-09-26/r2/restore-ref-a-devram-progress.log)、[最終 USB 状態](../../artifacts/hil/2026-09-26/r2/rig-final-status.log)。最終時点で Node1/2/4/5 は列挙、Node3 だけが OFFLINE。daemon は停止した。

## R1 から引き継いだ P7 と MemberEdhoc

[R1 報告](2026-09-26-bench-5node-r1.md) の P7 は C3 bridge/ref-a の console status→機器内 keygen→PoP challenge→DevCert→identity seal/readback まで通った。R1 MemberEdhoc は Node4 としての再 provision、Site Authority の join request→approve→member、GK2 readback、unicast 10/10、submit 1/1 を確認した。revoke は Site 側 commit と RS/GK epoch 1→2 を確認したが、旧 Node2 への RemovalNotice は unreachable、Site 台帳は allowed_unconfirmed のまま。JoinConfirm、GK ACK、旧 ID の物理的締め出し、手動 GK rotate、cutover は未完了。R2 はこれを完了扱いにせず、DevRam/睡眠試験用に rlsec を backup して切り替えた。
