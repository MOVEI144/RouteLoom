## #167：受信側 reset 後に end-to-end session が復旧しない

**真因**：DATA は end 保護される。受信側（Node2）が reset で RAM の end-to-end context を失うと、送信元（bridge = origin）は自分がまだ保持する古い context id で封をし続ける。受信側は link を RLD1 で 2 秒前後で再 BIND する一方、end frame は「未知 context id」で `AuthRequired` 拒否し、HopAccept も EndReceipt も返さない。無線上に「context を失った」信号はなく、送信元は再鍵を始める契機がない。session bank は未知 RX id に対し demand を記録しない設計（stranger RF 対策）なので、放置すると永久に 0 件配送になる。

**修正（設計 03 §9 の再handshake要求を受信側 end scope に実装、commit `503baae`）**：

- `SecurityProvider::note_rx_unknown_context()` を追加。`MeshNode` は link 認証済み frame の end open が `AuthRequired` のとき、この hook で提供者に報告する（`note_end_rx_refusal`）。
- `SessionBank::note_rx_unknown()` は origin（`context.sender`）への EndToEnd demand を記録する。owner の demand driver が RLRES1/EDHOC を origin へ開始し、origin の install が古い context を置き換える。10 秒以内に install した context があれば無視する（origin の install 進行中の遅延 frame に過剰反応しない）。link scope はここでは demand しない（RLD1 が近隣修復を担う）。
- coordinator の provider mux と RTC write-ahead wrapper が report を素通しする。

**host 回帰試験**：owner-sim に 2 件追加。`test_dev_destination_restart_without_report_stays_stale` は report 無しでは origin が古い cid のまま留まることを、`test_dev_destination_restart_recovers_end_session_from_rx_report` は report 1 回で 1 回の resume 交換内に双方向配送が戻ることを確認する。session bank と node の hook・guard も単体試験を追加。R7 の最終 source で GCC ASan ctest [95/95](../../artifacts/hil/2026-09-26/r7/asan-ctest.log)（329 秒）、docker `silkeh/clang:18` の clang ASan ctest [94/94](../../artifacts/hil/2026-09-26/r7/clang-asan-ctest.log)（187 秒。`routeloom_join_stack_gate` は tests/cpp/CMakeLists.txt で GCC 限定）。

- 「解除→初回配送完了」は runner が記録した offset_s（reset 解除から host が `delivered` を観測するまで）で、最小 3.026、中央値 3.488、最大 4.603 秒。runner の `recovery_s` は初回配送となった送信の admit 時刻（= 配送完了 − その latency）。

- cycle 5/7 が 8/10 なのは、RLD1 の最初の送信が boot 後 0.98 秒ではなく 2.52 秒に始まり（discovery の開始 jitter）、2 通目（+1.6 秒）も再 BIND 前に落ちたため。復旧自体は同じ経路で完了している。

**トレースが示す復旧の順序（cycle 0、Node2 console、時刻は Node2 の uptime ms）**：979 RLD1 tx（claim）→ 1,502 RLD1 rx（bridge の応答）→ 1,508 `BOUND peer=1` → 1,530 NeighborProbe(40) rx → 3,526 NeighborResult(41) rx → 3,528 `REACHABLE peer=1` → 3,588 古い cid（3137838671）の DATA(16) rx →`session unknown context`（新 hook が origin への demand を記録）→ 3,602 BootstrapAuth(3) tx（新 link cid で RLRES1 を origin へ）→ 3,623〜3,679 で 3/17 の交換と HopAccept(17) → host は解除後 3.284 秒に `delivered`。再 handshake 自体は約 100 ms で、復旧時間の大半は RLD1 の再 BIND（約 1.5 秒）と bridge 側の REACHABLE 判定（BOUND から NeighborProbe/Result 1 往復、約 2 秒）である。前段（R5〜R6）の診断 image では同じ位置で `session unknown context` を連発したまま送信側が新 cid へ切り替わらず 0 件配送だった。

## #167（付随）：復旧失敗中に端末 idempotency 表が埋まる

bridge の USB idempotency 表（16 件、保持 24 h）は期限内 record を追い出さないため、reset 復旧中に失敗した 16 送信で表が埋まり `IDEMPOTENCY_FULL` で以後の送信を 24 h 拒否していた。docs/spec/host.md §8 の host 側と同じく、mesh 配送が終端に達した（または受理拒否された）record を「settled」とし、満杯時は 5 秒の replay 保持を過ぎた settled record を古い順に追い出す。配送中の record は追い出さないので、本来の backpressure は保たれる。単体試験を追加。commit `6ae42a6`。R7 の 10×10（103 送信、うち 12 失敗）で `IDEMPOTENCY_FULL` は 0 件。

後続の修正では、追い出した identity の 64-bit digest を 96 件まで 24 時間保持する。旧 key の再送は `IDEMPOTENCY_WINDOW_EXPIRED`、墓標が満杯なら新規送信は `IDEMPOTENCY_FULL` で拒否し、同一操作の二重配送を防ぐ。R7 の実機数値はこの墓標追加前の image による測定であり、追加後の source は host 回帰試験と firmware matrix で検証した。reset runner の集計は送信受付と配送結果の両方で `IDEMPOTENCY_FULL` を検出するよう修正した。R7 の保存済み 100 件を配送結果から再集計しても同エラーは 0 件だった。現行の gateway は 24 時間で最大 112 個の異なる identity を受け付ける有界な実装で、これを超える継続運用には別の永続的な保持方式が必要である。

## #166：既定 C3 image の起動 heap 不足

**実測（C3、ESP-IDF v6.0.3）**：issue の既定 bridge（dedup 96、esp_netif 有効）は静的空き 20,512 B で link したが `esp_wifi_init` の heap 不足で起動せず、8 KiB の静的 floor は起動を保証していなかった。前段の dedup 32 件 image は静的空き 27,016 B で起動したが、ESP-NOW 開始後の heap は free 5,956 B・largest 3,968 B しか残らなかった。無線起動（Wi-Fi driver・PHY 校正・ESP-NOW）の消費は両 app で約 27.4 KB。

**修正（commit `66d6c1c`）**：ESP-NOW しか使わない firmware で不要な heap を削った。

- `ROUTELOOM_WIFI_NETIF_INIT`（既定 n）で lwIP の TCP/IP task 起動を任意化。ESP-NOW は Wi-Fi driver と default event loop だけで足りる。netif 有効時の bridge 起動後 free は 7,972 B、無効で 14,856 B（[有効](../../artifacts/hil/2026-09-26/r6/heap-netif-on/)、[無効](../../artifacts/hil/2026-09-26/r6/heap-netif-off/)）。
- C3 の既定 sdkconfig（bridge と reference）で A-MPDU（TX/RX）、余分な management buffer、softAP、enterprise、Wi-Fi NVS を無効化。reference にも bridge と同じ小さい RX/TX buffer 数を適用。
- 既定の bridge（C3 と C5）と C5 reference は dedup profile を relay 96 件から leaf 32 件にした。1 record 136 B なので静的 RAM −8,704 B。bounded admission の意味は変わらず、gateway が覚えておく中継 frame の数が減るだけで、terminal pin の上限（pool の 7/8）はそのまま。設計上の上限（link 32・end 128 session）は下げていない。
- `ROUTELOOM_BOOT_HEAP_FLOOR_BYTES`（既定 8 KiB）：ESP-NOW 起動後の free/largest heap を実測し、下回れば `BOOT_HEAP_BELOW_FLOOR` を log する（起動は継続）。HIL harness はこの行を起動失敗として扱う（commit `aaea506`、`flash.py` は flash 失敗、`reset_cycles.py` は `boot_failures` を数えて非 0 終了）。

**最終 source の image と実測（C3、R7）**：image はいずれも `tools/hil/build_image.sh` で最終 source から build し、sdkconfig・SHA-256・RAM report を各 directory に保存した。bridge の console は既定では UART0（未配線）なので、heap 行の読み取りには console を USB Serial/JTAG に向けた計測 image を使い、その後既定 image に戻した。
